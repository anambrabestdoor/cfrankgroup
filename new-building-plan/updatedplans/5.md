# PROMPT 3: STRICT MOBILE RESPONSIVENESS, ZERO HORIZONTAL OVERFLOW & SECURITY

Implement and verify the following requirements across the entire Anambra Best Door website and admin dashboard. These are mandatory requirements, not optional design improvements.

## 1. Mobile-First Responsive Design

- Build mobile-first, then adapt for tablets, laptops, and large desktop screens.
- Support screen widths from **320px upwards**, including 320px, 360px, 375px, 390px, 414px, 768px, 1024px, 1280px, and 1440px.
- All public pages, product pages, product archives, gallery, cart, WhatsApp ordering flow, login, password reset, and every admin screen must remain usable at these widths.
- Navigation must adapt appropriately to small screens. Use a functional mobile menu where necessary.
- Product grids, galleries, forms, tables, dialogs, buttons, typography, spacing, and images must resize or rearrange naturally.
- On mobile, replace wide admin tables with responsive layouts, stacked records, or clearly contained horizontal scrolling within the specific table region only when necessary.
- Ensure forms, inputs, dropdowns, modals, and rich-text editors fit the viewport and remain usable with touch controls and the on-screen keyboard.
- Keep buttons and interactive targets comfortably tappable. Avoid tiny controls, overlapping elements, clipped text, and content hidden behind fixed navigation.
- Use responsive images with appropriate sizing and aspect ratios. Prevent images and videos from forcing their parent containers wider than the viewport.
- Avoid fixed-width layouts, oversized minimum widths, and desktop-only interactions.
- Do not introduce unnecessary horizontal scrolling as a design choice.

## 2. Zero Unintended Horizontal Page Scrolling

**The entire document must not scroll horizontally at any supported viewport width.**

- Identify and fix the actual source of every overflow rather than hiding the problem with `overflow-x: hidden` on the body or document.
- Inspect common causes, including oversized images, long URLs and product names, wide tables, navigation menus, grids, flex children, fixed-width elements, absolute positioning, code/editor content, and third-party widgets.
- Use appropriate responsive CSS, `min-width: 0`, `max-width: 100%`, flexible grid columns, text wrapping, and component-level overflow handling where needed.
- Ensure product titles, specifications, prices, buttons, forms, and navigation do not push the page beyond the viewport.
- Where a genuinely wide element requires scrolling, such as a data table, contain that scrolling within its own component without causing page-level overflow.
- Do not break sticky headers, mobile menus, modals, or other interactions to achieve the overflow requirement.

### Mandatory automated verification

Use Playwright or an equivalent browser-based testing tool to test all major routes at the specified viewport widths.

At minimum, verify the document width against the viewport width using a check equivalent to:

`document.documentElement.scrollWidth <= document.documentElement.clientWidth`

Run this check on every important public route and admin screen, including states with the mobile menu open, dialogs displayed, long product names, and populated product tables.

A passing homepage alone is insufficient. Test the actual rendered application and fix every unintended overflow discovered.

Also test navigation, forms, product browsing, cart updates, and WhatsApp order initiation at mobile widths. Report any tests that could not be run and why.

## 3. Security Requirements

Treat security as a core architectural requirement, not a final cosmetic audit.

### Secrets and environment variables
- Never expose Supabase service-role keys, database passwords, private API keys, email provider secrets, or other privileged credentials in browser code, client bundles, public environment variables, HTML, logs, or source maps.
- Never use the `NEXT_PUBLIC_` prefix for secrets.
- Use server-only modules for privileged operations and environment variables or an appropriate secret manager for deployment.
- Provide an `.env.example` containing only placeholder values, never actual credentials.
- Public Supabase publishable keys may be used where appropriate, but only alongside correctly configured Row Level Security (RLS) and permissions.
- If a credential is discovered in source control or an exposed bundle, report it and recommend rotation. Do not claim rotation has happened unless it has actually been completed.

### Authentication and authorization
- Protect every admin route and every privileged server action/API endpoint.
- Enforce authentication and role-based authorization on the server. Hiding admin links in the UI is not access control.
- Verify that ordinary administrators cannot perform super-admin-only actions.
- Implement secure password reset using the supported authentication provider flow. Do not build an insecure custom password-storage system.
- Never store passwords in plaintext or create hardcoded production admin credentials.
- Prevent unauthorized users from creating or promoting themselves to administrator or super administrator.

### Supabase and database security
- Enable and verify RLS on all tables exposed through the Supabase Data API.
- Create explicit least-privilege policies for public product viewing, authorized product management, image storage, and administrative operations.
- Public users must not be able to modify prices, stock, product details, administrator roles, or other protected records.
- Validate and authorize every write operation on the server or through correctly enforced database policies.
- Store product images in appropriately configured storage buckets with access rules consistent with the intended public/private behavior.
- Never rely on client-side validation alone.

### Application security
- Validate and sanitize untrusted input on the server, including rich-text content, product fields, query parameters, and form submissions.
- Prevent cross-site scripting (XSS), injection, insecure direct object references, and unauthorized data access.
- Use secure session handling and appropriate cookie settings where applicable.
- Apply sensible request validation and rate limiting to authentication and other sensitive endpoints where supported.
- Do not expose stack traces, secrets, internal database details, or sensitive user information in production error messages.
- Avoid logging passwords, tokens, private credentials, or unnecessary personal data.
- Keep dependencies reasonably current and inspect security advisories relevant to the installed packages.

## 4. Required Security and Responsiveness Tests

Before declaring the project complete:

1. Run a production build and available type checks and lint checks.
2. Run automated responsive tests across the specified viewport widths.
3. Verify that every major route has no unintended document-level horizontal overflow.
4. Test protected admin routes while logged out.
5. Test privileged actions using accounts with different roles.
6. Verify that public users cannot modify protected Supabase records.
7. Inspect browser bundles and network responses for privileged keys or sensitive data.
8. Test form validation and malformed or unauthorized requests.
9. Test mobile navigation, dialogs, product cards, image galleries, admin forms, and table layouts.
10. Document any security checks that remain incomplete rather than claiming the application is secure without evidence.

## 5. Completion Gate

Do not declare the website production-ready merely because it builds successfully or looks good on a desktop.

Provide a concise report stating:
- Viewports and routes tested.
- Any horizontal overflow found and how it was corrected.
- Security controls implemented and the tests used to verify them.
- Build, type-check, lint, and test results.
- Remaining risks, limitations, or blocked tests.

Do not fabricate test results. If a test cannot be executed in the available environment, state that clearly.

**Priority order:** protect credentials and privileged data, enforce server-side access controls, eliminate unintended horizontal page scrolling, ensure practical mobile usability, and then polish the visual design. Preserve the supplied design references while adapting them responsively.

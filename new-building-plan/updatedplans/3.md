# ADDENDUM: WORDPRESS-STYLE PRODUCT EDITOR, SEO PANEL, INVENTORY MANAGEMENT & NOVICE-FRIENDLY ADMIN UX

## 1. OBJECTIVE

Build a complete, user-friendly product management experience inside the Anambra Best Door admin dashboard.

The dashboard must be suitable for a business owner or staff member who is not a developer, SEO specialist, or technical person.

Use the usability principles of WordPress and WooCommerce product editing, together with the focused SEO analysis and metadata workflow of Yoast SEO or Rank Math.

Do not copy their branding or interface verbatim. Build a simpler, purpose-built experience appropriate for Anambra Best Door.

**This must be a real content management interface connected to Supabase, not a visual mockup.**

The product editor must allow an administrator to manage:

- Product identity and descriptions.
- Product images and galleries.
- Product categories and attributes.
- Regular and selling prices.
- Stock availability and quantities.
- Product variations where needed.
- SEO titles, descriptions, keywords, and previews.
- Product publication status.
- Sales and ordering controls.
- Product-specific Jiji.ng listing links.
- Relevant shipping, delivery, and installation information.

Use sensible defaults, clear labels, contextual help, validation, and progressive disclosure so a novice can use the panel without understanding database schemas, HTML, JSON, or SEO terminology.

## 2. PRODUCT EDITOR LAYOUT

Create a dedicated product creation/editing interface, for example:

- `/admin/products/new`
- `/admin/products/[id]/edit`

Use a structured, WordPress-inspired layout.

### Recommended desktop layout

Use a wide main content area for product information and a narrower secondary column for publishing, pricing summaries, inventory status, and SEO health.

The interface may use tabs or grouped sections where this improves usability, but avoid hiding essential product fields behind too many clicks.

On mobile, collapse the secondary column into clearly labelled sections or a suitable stacked layout.

The editor should include:

1. Product name.
2. Product description editor.
3. Product images and gallery.
4. Product category and attributes.
5. Pricing.
6. Inventory and availability.
7. Product variations, if enabled.
8. Shipping, delivery, and installation details where relevant.
9. Search engine optimization.
10. Jiji.ng listing association.
11. Publishing controls.
12. Preview and validation.

Provide clear Save Draft, Preview, Publish, and Update actions as appropriate to the user's permissions and the product's current state.

Warn the administrator about unsaved changes before navigating away.

Do not create buttons that look functional but have no implementation behind them.

## 3. PRODUCT NAME AND CONTENT EDITING

### Product name

Provide a prominent product title field at the top of the editor.

Examples of legitimate product names might include:

- HFC Security Door.
- HFC Steel Security Door.
- Digital Smart Door Lock.
- Stainless Steel Door Handle.
- Modern Bathroom Door.

These are examples only. The administrator must be able to enter actual product names.

The product name should automatically be used as the default source for:

- Public product heading.
- Product page title fallback.
- Product archive card title.
- Default SEO title.
- Default image alternative text suggestions.
- WhatsApp order message.
- Product-related navigation and breadcrumbs.

Do not automatically overwrite manually customized SEO fields whenever the product name changes. Distinguish between generated defaults and administrator overrides.

### WordPress-like content editor

Provide a rich text editor for the full product description.

The editor should support common nontechnical editing tasks:

- Paragraphs.
- Headings.
- Bold and italic formatting.
- Bulleted lists.
- Numbered lists.
- Links.
- Undo and redo.
- Clear formatting.
- Useful paste behavior.

Use a maintained rich-text editing library compatible with the project's existing stack, if one is needed.

Do not expose a raw Markdown editor, Markdown syntax, HTML source, or a JSON editing field to the ordinary administrator.

The administrator should see the formatted content as they write it.

Store the resulting content in a safe, structured format and sanitize it appropriately before public rendering.

Provide a separate short description field for product cards, quick summaries, and introductory copy.

Include helpful placeholder guidance, such as:

"Describe the product, its main benefits, suitable applications, and what makes it useful to the customer."

Do not automatically publish generated filler descriptions or unsupported product claims.

## 4. PRODUCT IMAGES AND MEDIA

Provide a visual image-management panel with:

- Main product image.
- Additional product images.
- Drag-and-drop or click-to-upload.
- Image previews.
- Reordering of gallery images.
- Main-image selection.
- Image removal.
- Alternative text field for each image.
- Upload progress and error feedback.

The interface must make it obvious which image will appear first in the product archive.

Use Supabase Storage or the existing configured media service.

Validate file type and size. Generate suitable image variants or use the established image optimization pipeline.

Keep media URLs or Storage paths in the database, not embedded as hardcoded frontend assets.

For images without alternative text, suggest a descriptive value based on the product and image context, but allow the administrator to edit it.

Do not automatically use the same SEO keyword phrase for every image.

### Categories

Allow the administrator to:

- Select an existing category.
- Search categories.
- Create a category if their permissions allow it.
- Assign a primary category.
- Assign additional categories only when the data model and site structure support them.

Categories should be database-managed, with their own slugs, descriptions, and SEO fields.

Examples might include:

- Security Doors.
- Steel Doors.
- Interior Doors.
- Door Handles and Locks.
- Smart Door Locks.
- Windows.
- Sanitary Wares.

Only create categories relevant to the actual business inventory.

### Product attributes

Provide a simple interface for adding specifications without writing code.

Examples:

- Material.
- Colour.
- Dimensions.
- Finish.
- Lock type.
- Door orientation.
- Manufacturer or brand.
- Model.
- Warranty, when confirmed.
- Other product-specific specifications.

Allow the administrator to add custom attribute labels and values when necessary.

Use structured data internally rather than requiring the administrator to type specifications into a single unstructured text field.

Display suitable attributes on the public product page.

### Product tags

Optionally support descriptive product tags for internal organization or useful browsing.

Do not automatically generate hundreds of tags or create indexable tag pages without an SEO justification.

## 6. PRICING AND COMMERCIAL INFORMATION

Create a clearly labelled pricing panel.

Include:

- Regular price.
- Selling price.
- Currency.
- Optional price-on-request setting.
- Optional minimum order quantity, if relevant.
- Optional sale start and end dates, if time-limited promotions are genuinely required.

For Anambra Best Door, NGN should be the default currency unless the business explicitly supports additional currencies.

### Price behavior

- Display the selling price prominently.
- Display the regular price as a comparison only when appropriate.
- Calculate discounts correctly.
- Do not display a fake discount when prices are equal.
- Do not treat a missing price as zero.
- Support price-on-request products.
- Validate that numeric prices are nonnegative.
- Use a monetary representation that avoids floating-point precision errors.

If sale scheduling is implemented, calculate the effective price consistently on the server and use the same result in product cards, detail pages, structured data, and WhatsApp order messages.

When a product price changes, the current price should be reflected after the appropriate cache revalidation.

The admin should not need to edit multiple pages to change one product price.

## 7. INVENTORY AND AVAILABILITY MANAGEMENT

Inventory management is a core requirement.

The administrator must be able to mark a product as sold out, set its available quantity, and communicate whether customers can order it through WhatsApp.

Provide a dedicated, easy-to-understand inventory panel.

### Inventory fields

Support:

- Enable or disable stock tracking.
- Stock quantity.
- Availability status.
- Low-stock threshold.
- Allow or disallow ordering when out of stock.
- Optional SKU.
- Optional barcode or supplier reference, if useful.
- Optional backorder status.
- Optional estimated restock message.
- Optional stock notes visible only to authorized administrators.

### Availability statuses

Support at least:

- In stock.
- Low stock.
- Out of stock / Sold out.
- Made to order.
- Contact for availability.

Use clear labels rather than requiring the administrator to understand database status codes.

For example, the editor might show:

**Stock status:** In stock

**Available quantity:** 12 pieces

**Low-stock warning:** Notify me when 3 pieces remain

The public product page could display "12 pieces available" when the business chooses to show exact quantities. Otherwise, show a simpler "In stock" label.

The administrator should be able to choose whether exact stock counts are visible to customers.

### Inventory behavior

- Prevent negative stock quantities.
- Do not mark an item as in stock if stock tracking is enabled and the available quantity is zero.
- Allow the administrator to manually mark an item as sold out.
- Handle the distinction between stock tracking being disabled and actual zero stock.
- When a product is sold out, show the correct status on the product page and archive card.
- Disable or appropriately change Add to Cart and WhatsApp order actions according to the product's orderability.
- Allow a sold-out product to remain published so its product page and search visibility can be preserved.
- Offer a WhatsApp availability inquiry or restock inquiry if the owner wants it.
- Prevent misleading product structured data from declaring a sold-out product in stock.

When stock is restored, the public status should update automatically after cache revalidation.

### Important inventory integrity rule

The website uses WhatsApp orders and has no automated checkout. Therefore, adding an item to the local cart must not reduce inventory.

Opening WhatsApp must not reduce inventory either.

A browser cart is not a confirmed sale.

For this version, the administrator should update quantities manually when stock changes.

If an administrator later needs to record confirmed sales or manage inventory movements, implement a separate protected stock-adjustment or order-recording workflow. Do not pretend the website knows about purchases completed in WhatsApp.

## 8. PRODUCT VARIATIONS

Some products may be available in different sizes, colours, materials, finishes, dimensions, or configurations.

Support variations when they are relevant.

Examples include:

- A door offered in multiple sizes.
- A handle offered in different finishes.
- A product available in several colours.
- A lock available in different models.

Do not force every product into a variation system if most products have one fixed configuration.

### Variation capabilities

Where variations are enabled, support:

- Attribute combinations.
- Variation-specific SKU when required.
- Variation-specific price where needed.
- Variation-specific stock quantity where needed.
- Variation-specific availability.
- Optional variation image.
- Selection of a valid combination on the public product page.

A selected variation must affect the displayed price, availability, and WhatsApp order details correctly.

If variations are not yet needed for the initial catalogue, design the data model so they can be introduced later without rewriting all product logic.

Do not implement a fake variation selector that does not change the actual product data.

## 9. SEO PANEL — YOAST/RANK MATH-INSPIRED WORKFLOW

Create a dedicated SEO panel within the product editor.

It must be a genuine working feature, not just a set of empty text fields.

Use the usability principles of Yoast SEO or Rank Math, simplified for the business owner.

### SEO fields

Support:

1. Focus keyphrase.
2. Additional related keyphrases, optionally.
3. SEO title.
4. Meta description.
5. URL slug.
6. Search-result preview.
7. Social-sharing title.
8. Social-sharing description.
9. Social-sharing image.
10. Indexing directive, with safe defaults and suitable permissions.
11. Canonical URL override only where necessary.
12. SEO analysis and recommendations.

For a product such as "HFC Security Door", the administrator should be able to enter a focus keyphrase such as "HFC security door".

Other possible keyphrases might include the exact product type, material, model, or a relevant commercial phrase, but only when they accurately describe that product.

Do not require the administrator to know what canonical URLs or robots directives mean. Put advanced controls in a clearly labelled Advanced SEO section with short explanations and sensible defaults.

### Automatically generated defaults

When creating a product:

- Generate a slug from the product name.
- Suggest an SEO title from the product name and brand where appropriate.
- Generate a reasonable meta description from the product summary when available.
- Suggest a focus keyphrase based on the product name.
- Suggest image alternative text.
- Build the canonical URL from the configured production domain and the actual product slug.
- Use the default social image when a custom image has not been selected.

Allow the administrator to override generated values.

If the product name changes, update generated defaults only when the corresponding field has not been manually customized.

### Search-result preview

Display a live preview that resembles a Google search result.

Show:

- Site or breadcrumb path.
- SEO title.
- URL.
- Meta description.

Update the preview when the administrator edits the SEO title, slug, or meta description.

The preview is an approximation, not a guarantee of how Google will display the page.

### Focus keyphrase analysis

Provide lightweight, deterministic SEO checks that inspect the actual product data.

Possible checks:

- Is the focus keyphrase set?
- Does the keyphrase accurately match the product?
- Does the SEO title describe the product?
- Does the title include the keyphrase naturally when appropriate?
- Does the meta description exist and accurately summarize the product?
- Is the URL slug descriptive?
- Is the product description sufficiently informative?
- Is the main product image present?
- Does the main image have useful alt text?
- Are product specifications provided where relevant?
- Does the product have a category?
- Is the product internally linked through its category or related products?
- Is the product indexable?
- Does the page have a valid canonical URL?
- Are required product details available for structured data?

Show clear statuses such as:

- Good.
- Needs improvement.
- Missing information.

Provide specific suggestions in plain English.

For example:

"Your product title is clear, but the search description is empty. Add a short description explaining the product and its main benefit."

Or:

"Your product image does not have alternative text. Describe what the image shows so users with screen readers can understand it."

### SEO scoring rules

If a numerical score is implemented, define the checks and weighting transparently.

Do not present the score as a Google ranking factor or claim that a 100/100 score guarantees rankings.

Avoid punishing a product for not including a keyphrase an arbitrary number of times.

Do not require exact-match keyword repetition, unnatural keyword density, or unnecessary long descriptions.

Content usefulness, search intent, factual accuracy, technical accessibility, and real business relevance matter more than a cosmetic score.

### Additional keyphrases

Allow related phrases to be entered when useful.

Analyze them without forcing every phrase into the SEO title or description.

Do not automatically generate a separate landing page for each related phrase.

### Save behavior

SEO fields must persist to Supabase and be available when the product is reopened.

Use proper validation and distinguish between saved and unsaved changes.

The public metadata generation must actually use the saved SEO fields. Do not build a working-looking SEO panel whose values never reach the rendered product page.

## 10. SEO FIELDS MUST DRIVE THE PUBLIC WEBSITE

The database, editor, and public frontend must use a single coherent product data model.

When an administrator saves a product, the relevant changes should propagate to:

- Product detail page.
- Product archive.
- Category listings.
- Homepage featured-product section, where applicable.
- Page title and meta description.
- Open Graph and social-sharing metadata.
- Canonical URL.
- Product JSON-LD.
- Sitemap inclusion and last-modified information.
- WhatsApp order messages.
- Related product links.
- Availability indicators.
- Product images and alternative text.

Implement appropriate caching and revalidation so changes become visible promptly.

For example, publishing a product should make it eligible for inclusion in the catalogue and sitemap. Unpublishing it should remove it from public listings and the sitemap, with the established redirect or not-found policy applied to its URL.

When a slug changes, update internal references and establish an appropriate redirect from the old slug where feasible.

Do not allow admin fields and public pages to drift out of sync.

## 11. PUBLISHING WORKFLOW

Provide a familiar publishing model.

Support:

- Draft.
- Published.
- Unpublished or archived, as appropriate.
- Optional scheduled publishing if the feature is genuinely needed.

The administrator should be able to save an incomplete product as a draft without making it public.

Before publishing, show a concise readiness checklist, such as:

- Product name provided.
- Category selected.
- Selling price or price-on-request status configured.
- Product image uploaded.
- Description provided.
- Availability configured.
- SEO metadata reviewed.

Treat some fields as recommendations rather than universal hard requirements. For example, a product may legitimately have no regular price or exact stock count.

Show warnings for missing optional information instead of blocking every publication.

Require confirmation for destructive actions and clarify whether an action unpublishes, archives, or permanently deletes a product.

## 14. ACCESSIBILITY AND NOVICE-FRIENDLY UX

The admin editor should not feel like a developer control panel.

Use:

- Plain-language labels.
- Short explanations next to unfamiliar concepts.
- Helpful examples.
- Sensible defaults.
- Visible save status.
- Field-level validation.
- Clear error messages.
- Confirmation for destructive actions.
- Searchable category selectors.
- Visual image previews.
- Readable stock indicators.
- Responsive forms.
- Keyboard accessibility.
- Clear focus states.

Avoid requiring the administrator to edit JSON, YAML, raw HTML, Markdown, SQL, or environment variables during routine product creation.

Keep advanced SEO and technical settings available without making them the first thing a novice sees.

Use progressive disclosure: essential content and pricing fields first, advanced settings later.

Do not use excessive tooltips as a substitute for clear labels.

## 15. TESTING REQUIREMENTS FOR THE PRODUCT EDITOR

Verify the following end-to-end.

### Content

- Create a product with a rich description.
- Save it as a draft.
- Reopen and edit it.
- Publish it.
- Confirm that the formatted description renders correctly.
- Confirm that the product appears in the correct public category.

### SEO

- Change the focus keyphrase.
- Edit the SEO title and meta description.
- Observe the preview updating.
- Save and reopen the product.
- Confirm the public page uses the saved metadata.
- Confirm the canonical URL is correct.
- Confirm structured data reflects the product's actual price and availability.
- Confirm unpublished products are not included in the sitemap.

### Inventory

- Create an in-stock product.
- Set a quantity.
- Mark a product as sold out.
- Confirm archive and product page indicators update.
- Confirm order actions respect availability.
- Restore stock and verify the public state updates.
- Confirm the local cart does not automatically reduce inventory.

### Pricing

- Enter regular and selling prices.
- Confirm correct discount calculations.
- Test missing regular price.
- Test price-on-request products.
- Test zero-valued inputs and invalid negative values.
- Confirm all public price displays remain consistent.

### Images

- Upload a main image.
- Add and reorder gallery images.
- Edit alternative text.
- Confirm image order and alt text on the public page.
- Verify unsupported or oversized uploads are rejected safely.

### Authorization

- Confirm ordinary visitors cannot edit products.
- Confirm unauthorized users cannot modify prices, stock, or SEO fields through direct requests.
- Confirm administrator role boundaries are enforced.

### Final acceptance criterion

The product editor is complete only when a nontechnical administrator can create, describe, price, categorize, optimize, publish, and manage the inventory status of a product from the dashboard, and the public website correctly reflects those changes without editing source code.
